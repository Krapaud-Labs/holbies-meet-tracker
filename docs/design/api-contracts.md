# Contrats API

## Invariants identité et token (CR-011/012/013)

- Les comparaisons d'identité retirent les espaces périphériques et normalisent NFC; elles conservent exactement la casse de la partie locale et passent le domaine en minuscules. Les points et suffixes `+` sont conservés. Nom, translittération, partie locale seule et ordre d'entrée ne rapprochent jamais deux personnes. Aucun provider ID ou alias n'est actuellement utilisé.
- Pour Agenda/Meet et les statuts backend, un match nominal seulement, une identité manquante, un conflit un-à-plusieurs, un événement/snapshot non corrélé ou un roster incomplet produit `identity-to-check` / « à vérifier ». Ce résultat n'est ni présent ni absent et reste déterministe dans toutes les permutations. `absent` n'est déterminable que si une clé e-mail comparable est disponible côté roster et côté Meet, après fin de réunion et collecte/pagination complète sans erreur, sans match ni candidat ambigu. Si l'e-mail Meet manque, cas courant, l'identité reste « à vérifier », jamais absente. Aucune People API ni aucun scope supplémentaire n'est utilisé pour contourner cette limite.
- Toute valeur OAuth provenant de `popup.js` ou de `background.js:getToken()` doit être une chaîne non blanche avant état connecté, affectation courante ou appel réseau. `background.js:googleJson` et `syncEvent` n'envoient aucun fetch Google ou backend avec en-tête `Bearer` avant cette garde. Valeur truthy non textuelle, blanche ou absente : zéro fetch et aucune fuite dans erreur, DOM ou journal. Dans la popup, un résultat invalide donne zéro requête, un message générique et le retour CSV. L'export Sheets ne remplace pas le token valide utilisé par Agenda/Meet avant validation du nouveau résultat.

> Les contrats Google servent la cible MVP. Les endpoints Backend Live ci-dessous décrivent le suivi as-built et les fonctions live générales Post-MVP. Le flux de job CR-008 et les états de cycle de vie sont proposés dans `meet-flow.md` et `data-model.md`. Les endpoints d'authentification serveur, de dépôt/retrait du rapport CR-009, ainsi que les payloads et règles d'erreur restent à concevoir; rien de cela n'est implémenté.

- Google Calendar `events.list` : comportement actuel, calendrier primaire seulement; cible CR-001, événements de tous les agendas suivis dans les réglages, avec pagination complète et filtrage local sur les fenêtres d'événements à Meet.
- Google Meet `conferenceRecords.list`, `participants.list` et `participantSessions.list` : lecture des comptes rendus et sessions.
- `ConferenceRecord.endTime` est renseigné pour une conférence passée; `ParticipantSession.endTime` apparaît lorsque la session est terminée. Le schéma REST `Participant` ne fournit pas d'e-mail : il expose `signedinUser`, `anonymousUser` ou `phoneUser`; `signedinUser` comprend `user` et `displayName`. L'utilisateur décide de ne pas ajouter People API ni de scope supplémentaire. Les étudiants non reliables restent « à vérifier », ne comptent ni présents ni absents et un rapport issu d'une collecte complète peut être exporté comme « PARTIEL », jamais complet. Une demande ultérieure pour établir une correspondance via People API devra être séparée. Sources officielles vérifiées le 2026-10-24 : [Participant Meet](https://developers.google.com/workspace/meet/api/reference/rest/v2/conferenceRecords.participants) et [guide Meet participants](https://developers.google.com/workspace/meet/api/guides/participants).
- Vérification préalable de CR-001 : le code as-built utilise le compte Google OAuth connecté pour appeler `conferenceRecords.list` par code Meet, puis les endpoints participants et sessions. Le classeur du 16/10 confirme une sortie non vide, sans révéler le compte OAuth, le rôle du mentor sur l'espace ni les réponses API. Aucune exigence de rôle administrateur Workspace n'est établie. La cible inclut les réunions auxquelles participe le compte connecté même lorsqu'un autre mentor les a organisées; aucun rapport inter-mentors n'est visé. `conferenceRecords.list` ne retourne que les conférences organisées par l'appelant. **Voie documentée pour le collecteur VPS, non validée en intégration** : obtenir le code depuis l'événement Agenda, appeler `spaces.get` pendant la conférence, capturer `activeConference.conferenceRecord`, puis utiliser `conferenceRecords.get` et `participants.list` sur l'identifiant connu. Google indique qu'un participant peut lire les ressources participants et sessions d'un record connu. Le scope `meetings.space.readonly` est déjà dans `manifest.json:23`. La séquence de découverte et les autorisations du principal serveur par mentor restent à prouver. La capture doit avoir lieu avant la fin; elle ne dépend pas de Chrome. Le `meetingCode` est supprimé à la fin du job; le `conferenceRecordId` est supprimé après finalisation ou sa rétention temporaire explicitement définie pour revue. Les quotas, les retries et la réconciliation après job manqué restent à concevoir. Sources relues le 2026-10-24 : [espaces Meet](https://developers.google.com/workspace/meet/api/guides/meeting-spaces-overview), [participants Meet](https://developers.google.com/workspace/meet/api/guides/participants), [conferenceRecords.get](https://developers.google.com/workspace/meet/api/reference/rest/v2/conferenceRecords/get), [conferenceRecords.list](https://developers.google.com/workspace/meet/api/reference/rest/v2/conferenceRecords/list), [authentification et scopes](https://developers.google.com/workspace/meet/api/guides/authenticate-authorize).
- Le domaine étudiant `@holbertonstudents.com` sert au rapprochement du roster Agenda; il ne confère pas de droits Meet. `participants.list` utilise obligatoirement `fields=participants(signedinUser(user)),nextPageToken` et compare les `user` au `sub` OpenID. Ce masque limite les champs retournés, pas les personnes : les identifiants `users/{user}` de tous les participants connectés présents dans les pages sont lus transitoirement. Seul l’identifiant correspondant au mentor peut être conservé après correspondance; les autres ne doivent être ni persistés, journalisés ou transmis. L’API n’offre pas de filtre serveur par `signedinUser.user`. Sans `fields`, Google renvoie par défaut `participants/*`; échec fermé si le masque ne peut être appliqué. Références officielles : [participants.list](https://developers.google.com/workspace/meet/api/reference/rest/v2/conferenceRecords.participants/list), [guide des participants](https://developers.google.com/workspace/meet/api/guides/participants) et [guide des conférences](https://developers.google.com/workspace/meet/api/guides/conferences), consultés le 2026-10-23.
- Google Drive `files.create` avec `mimeType=application/vnd.google-apps.spreadsheet`, dossier parent fixe et `appProperties` privée, puis Google Sheets `spreadsheets.values.update` pour écrire les cellules. Google Drive `files.list` ne sert qu’à retrouver une création incertaine par propriété, sans relancer automatiquement la création.
- Backend `PUT /api/v1/live/sessions/{id}/participants` (Post-MVP) : snapshot de participants envoyé par un client autorisé pour alimenter le suivi live sans Pub/Sub. Chaque entrée accepte `name`, `email`, `joinedAt` et `leftAt`; le serveur recalcule le statut et le retard. Une présence reste possible si la clé e-mail complète est comparable. Aucun client actuel n'apporte au serveur une preuve vérifiable de `ConferenceRecord.endTime` et de la pagination complète; les invités attendus non observés restent donc `identity-to-check` / « à vérifier », jamais absents. Ne pas ajouter de booléen client comme preuve de complétude.
- Backend `POST /api/v1/live/sessions/{id}/end` (Post-MVP, comportement as-built) : clôture authentifiée d'une session après la fin Agenda et une marge de dix minutes. Le comportement historique qui transforme les invités non observés en absents est supersédé dans la cible QLT-003 par la règle fail-closed ci-dessus. Une capacité d'absence backend nécessite un CR et un work item distincts pour concevoir et prouver la collecte complète côté serveur; aucun marqueur client non fiable ne la remplace.

Les réponses HTTP non réussies sont affichées comme erreurs utilisateur, avec le détail API lorsqu'il est exploitable. Les listes paginées suivent `nextPageToken`.

## Contrats logiques CR-008/CR-009 à concevoir

> **Ces opérations sont des exigences de contrat, pas des routes ou endpoints approuvés.** Les méthodes HTTP, chemins, schémas exacts, sessions, en-têtes d'authentification et codes d'erreur du VPS restent `needs-review`; ne pas les implémenter sur la seule base de ce tableau.

### Décisions de protocole non prises

Les opérations de début/callback OAuth, statut de session, révocation, job interne, liste/téléchargement/accusé/suppression du buffer n'ont pas de routes finales. Le protocole de preuve d'identité du VPS vers la popup, la prévention de rejeu, la pagination, les erreurs stables, les retries, les limites de taille, la version du rapport et l'idempotence du retrait doivent être spécifiés avec une revue sécurité. Le tableau délimite les obligations à couvrir, sans figer une API ou un mécanisme cryptographique.
